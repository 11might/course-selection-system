==========================================================
一、给下一次对话的 AI —— 请先读这段
==========================================================

这个项目的学习文档**只有 Word（.docx）**，没有 md 源文件了。
你要读或改它们，**不要**去找 .md，直接用 docs\_docx_tool.py：

  先看全文（带段落号）：   python docs\_docx_tool.py read "docs\给新Agent交接手册.docx" --out C:\Temp\dump.txt
  找关键词定位：           python docs\_docx_tool.py find "docs\学习日记汇总.docx" 2026-09-19
  改某一段（先预览）：     python docs\_docx_tool.py replace "docs\给新Agent交接手册.docx" 58 "新文字"
  确认后写盘：             在上面那条末尾加 --apply
  往中间插一段：           python docs\_docx_tool.py insert "docs\给新Agent交接手册.docx" 58 "新文字" --apply
  删除某一段：             python docs\_docx_tool.py delete "docs\给新Agent交接手册.docx" 189 --apply
  文末续写一段：           python docs\_docx_tool.py append "docs\学习日记汇总.docx" "## 续写：..." --apply

各文档分工（2026-09-19 用户确认）：
  - 学习日记汇总.docx —— **只往下加当天做了什么，不改上面已写的**。
  - 给新Agent交接手册.docx / 学习进度与技术说明.docx —— 记最新状态，按代码变化更新。
  - 但要**保留成长痕迹**：比如密码「一开始明文 → 后来改加密」，就写成前后对比，
    别把旧状态抹掉。只有明显的事实错误（说某文件不存在其实存在、说没提交其实提交了）
    才直接改掉或删除。

铁律：
  1. **改前先 commit 存档。** docx 是二进制，git 看不见改了啥，只能整份存。
  2. **replace 只按段落号改，不要按关键词批量替换。**
     （2026-09-19 教训：按关键词替换一次冲掉 6 段，只能从 git 捞原文重做。）
     想批量改，先 find 出段落号，逐个 replace。
  3. 改完自己 read 一遍验证，再告诉用户。
  4. 找不到段落号就越界报错；段落号从 0 开始，**每次改动后编号会变**，重新 find。

第一优先读：给新Agent交接手册.docx（环境 / 禁区 / 教学习惯 / 真实进度）。
权威口径：每日学习时间表与督学约定.docx（休息日 / 强度 / 债；9 月排班需用户重确认）。

三、文档工作流（2026-09-19 用户确认）
==========================================================

- 每次学习结束后，Agent **主动**更新 Word：交接手册（过期处同步）+ 日记（续写当天），
  不用再问要不要改；但覆盖 Word 前先 commit，且改完给用户看结果。
- 时间表里的排班、时长、债，以用户口述为准，Agent 不擅自改。
- 旧 md 的完整内容留在 git 历史里（提交 70d0b60），需要原文时：
    git show 70d0b60:"docs/给新Agent交接手册.md"
    git checkout 70d0b60 -- "docs/给新Agent交接手册.md"   （会把 md 恢复到工作区）
- 想恢复某个 docx 的旧版本：
    git checkout <commit> -- "docs/学习日记汇总.docx"
